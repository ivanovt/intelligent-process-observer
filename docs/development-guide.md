# Development Guide — Intelligent Process Observer

This guide defines the initial development workflow for the Intelligent Process Observer repository. It is intentionally minimal: the goal is to make local development, testing, specification, and review easy before introducing additional tooling.

> **Quick contributor workflow:** See [`development-workflow.md`](development-workflow.md) for the concise OpenSpec → review → implementation → archive process and reusable skill reference. This document remains the detailed environment/setup guide.

## 1. Scope of this guide

This guide starts at repository level. It assumes the host environment already provides:

- Windows with WSL2;
- Ubuntu 22.04 LTS inside WSL2;
- VS Code with WSL support;
- Git;
- Docker Engine running directly inside WSL2;
- `uv`;
- Node.js 24 LTS and npm;
- Codex CLI and/or the VS Code Codex integration;
- OpenCode if it will be used;
- the OpenSpec CLI.

The repository should live in the WSL Linux filesystem, for example:

```bash
~/projects/intelligent-process-observer
```

Avoid keeping the working tree under `/mnt/c/...` for normal development.

This guide does not install host-level tools. It explains how to bootstrap and operate the repository after cloning it.

## 2. Core development principles

The repository follows a few explicit rules:

1. Keep the development setup minimal until a real need justifies additional tooling.
2. Architecture and implementation specifications are separate concerns.
3. Architecture documents and ADRs are authoritative for architectural decisions.
4. OpenSpec defines concrete feature/change behavior and acceptance criteria.
5. Small, mechanical, unambiguous changes may bypass OpenSpec.
6. New or changed behavior must be specified through OpenSpec before implementation.
7. Human approval is required before an agent starts implementing an OpenSpec change.
8. Agents stop instead of inventing unresolved architectural decisions.
9. `main` is protected; work enters it through pull requests and squash merges.
10. `make check` is the canonical local pre-PR verification gate.

## 4. Sources of truth

### 4.1 Architecture

`docs/architecture/` is the architectural source of truth. It contains concepts, runtime semantics, component responsibilities, structured contracts, ADRs, open decisions, glossary, and change history.

Use the architecture package's precedence rule:

```text
newer ADR
  > current concept / architecture / contract document
  > older example / working note
```

An item marked `Open` is not a requirement. An item marked `Deferred` is intentionally outside the current MVP unless explicitly brought back into scope.

### 4.2 OpenSpec

Use OpenSpec for concrete behavioral work:

```text
openspec/changes/
→ behavior currently being proposed or implemented

openspec/specs/
→ accepted functional behavior accumulated from completed changes
```

Do not copy the architecture package into OpenSpec. A change should reference the relevant architecture files and ADRs.

### 4.3 Code

Source code is the implementation of the approved architecture and OpenSpec behavior. Code does not override the architecture or an approved specification merely because the implementation is easier another way.

## 5. Language convention

All new development-facing repository content is written in English:

- source code and identifiers;
- comments;
- `AGENTS.md`;
- root `README.md`;
- development documentation;
- OpenSpec proposal/spec/design/task artifacts;
- pull-request text.

The existing architecture package remains in Bulgarian. Do not create a second English mirror unless that is explicitly approved later.

## 5.1 Alert pipeline integration boundary

The Alert pipeline receives a provider and an analysis agent through framework-neutral
ports. Production composition supplies those dependencies and opens the caller-owned
transaction only after provider acquisition, normalization, deterministic analysis,
optional tools, agent work, and result construction finish. The terminal persistence
composer then advances the existing LensRun and conditionally writes its artifact; it
flushes but never commits. Jira transport, credentials, field mapping, and production
model/provider selection remain intentionally deferred and must not be added as defaults.

## 6. Initial bootstrap workflow

The repository bootstrap is a one-time workspace change and is not itself an OpenSpec change.

Create a branch from `main`:

```bash
git switch main
git pull --ff-only
git switch -c chore/bootstrap-workspace
```

Copy the bootstrap files into the repository, then initialize tool-generated OpenSpec integrations as described below.

### 6.1 Verify host tools

The project uses minimum-version policy rather than strict host-tool pinning. Verify the important tools:

```bash
python3 --version
uv --version
node --version
npm --version
docker --version
docker compose version
openspec --version
codex --version
```

The system Python shipped with Ubuntu may remain older. The backend project requires Python >= 3.13 and is managed by `uv`; do not replace Ubuntu's system Python.

If `uv` cannot find a compatible Python when syncing the backend, install a project-capable interpreter through `uv` and retry:

```bash
uv python install 3.13
```

This does not change the system Python.

### 6.2 Initialize OpenSpec integrations

OpenSpec integration files should be generated by the installed CLI instead of hand-written. From the repository root:

```bash
openspec init --tools codex,opencode --profile core
```

Before accepting any cleanup prompt, review what OpenSpec says it will remove or replace, especially if the machine has been used with older OpenSpec versions.

After init:

1. read the exact "Getting started" output;
2. inspect the generated `.agents/` and OpenCode-specific files;
3. restart/reload the assistant if it only discovers skills at startup;
4. commit the generated OpenSpec tool files with the repository.

Codex is skills-only in the current OpenSpec workflow. Its generated skills use the `.agents/skills/openspec-*` layout. Codex invocation names include forms such as:

```text
$openspec-explore
$openspec-propose
$openspec-apply-change
$openspec-update-change
$openspec-sync-specs
$openspec-archive-change
```

OpenCode may expose generated commands or skills with a different spelling. Use the exact invocation form printed by `openspec init` and represented by the generated files rather than assuming the Codex syntax applies to OpenCode.

When the global OpenSpec CLI is upgraded, refresh generated integration files from the repository root:

```bash
openspec update
```

Review and commit the generated diff.

### 6.3 Prepare application dependencies and local env files

Run:

```bash
make setup
```

This command is intentionally safe and narrow. It:

- creates `.env` from `.env.example` only when `.env` does not already exist;
- creates `frontend/.env` from `frontend/.env.example` only when it does not already exist;
- runs `uv sync` in `backend/`;
- runs `npm install` in `frontend/`.

It does not:

- start PostgreSQL;
- run migrations;
- start backend/frontend processes;
- overwrite existing local `.env` files.

The first successful setup generates dependency lockfiles. Verify that these exist and commit them in the bootstrap PR:

```text
backend/uv.lock
frontend/package-lock.json
```

Do not hand-author fake lockfiles.

### 6.4 Start PostgreSQL

```bash
make db-up
```

Inspect service state when needed:

```bash
docker compose ps
```

Stop the service with:

```bash
make db-down
```

Only PostgreSQL is containerized for daily development. The FastAPI and Vite processes run directly inside WSL for faster reload/debugging.

### 6.5 Start the backend

```bash
make backend
```

The bootstrap backend provides a shallow health endpoint:

```bash
curl http://localhost:8000/health
```

Expected response:

```json
{"status":"ok"}
```

`/health` checks only that the FastAPI process is serving requests. It intentionally does not query PostgreSQL. A dependency/readiness endpoint can be introduced later if an actual runtime requirement calls for one.

### 6.6 Start the frontend

In another terminal:

```bash
make frontend
```

The bootstrap frontend is an independent React + TypeScript + Vite application. It does not call the backend yet. No end-to-end smoke path, UI component library, Tailwind setup, or frontend test framework is added during bootstrap.

### 6.7 Run local verification

```bash
make check
```

The initial check gate runs:

```text
backend  → Ruff lint
backend  → Ruff format check
backend  → pytest
frontend → ESLint
frontend → production build
OpenSpec → strict structural validation
```

OpenSpec validation checks specification/change structure. It does not prove that code implements the specification or that an implementation respects every ADR; those remain test/review responsibilities.

### 6.8 Commit and open the bootstrap PR

After all checks pass:

```bash
git status
git add .
git commit -m "chore: bootstrap development workspace"
```

Pushing and opening the PR remain explicit user actions under the conservative agent policy.

The PR should target `main`. Use the repository PR template, require CI to pass, review the changes, and squash merge.

## 7. Canonical Makefile commands

The root `Makefile` is the canonical interface for common local operations.

| Command | Purpose |
| --- | --- |
| `make setup` | Sync/install local dependencies and create missing local env files. |
| `make db-up` | Start the local PostgreSQL service. |
| `make db-down` | Stop/remove local Compose services while preserving the named DB volume. |
| `make backend` | Run FastAPI with reload in WSL. |
| `make frontend` | Run the Vite development server in WSL. |
| `make lint` | Run Ruff lint and frontend ESLint. |
| `make format` | Apply Ruff formatting to Python code. |
| `make test` | Run backend pytest. |
| `make check` | Run the complete local pre-PR verification gate. |

Keep the Makefile thin. If a target begins accumulating substantial logic, reassess whether that logic belongs in the actual tool configuration or a deliberately approved script rather than hiding it in Make recipes.

## 8. Environment and secrets

### 8.1 Root environment

The root `.env.example` documents local backend/PostgreSQL settings. `.env` contains local values and is ignored by Git.

Initial variables:

```text
APP_ENV
POSTGRES_USER
POSTGRES_PASSWORD
POSTGRES_DB
POSTGRES_PORT
DATABASE_URL
```

The committed default credentials are only for local development.

### 8.2 Frontend environment

Use `frontend/.env.example` and `frontend/.env` for client-side Vite variables only.

Any `VITE_*` value may become visible in the browser bundle. Never place an API key, password, LLM secret, database credential, or other secret there.

## 9. Database workflow

PostgreSQL runs in Docker Compose, while SQLAlchemy/Alembic run from the backend process environment in WSL.

The initial bootstrap provides:

- SQLAlchemy async engine/session factory primitives;
- Psycopg 3 driver support;
- Alembic configuration and async migration environment;
- no domain tables and no initial domain migration.

Once an approved feature introduces a schema change, an agent may generate and edit Alembic migrations and apply normal migrations locally.

Typical commands, run from `backend/`, are:

```bash
uv run alembic revision --autogenerate -m "describe change"
uv run alembic upgrade head
```

The schema change itself must already be inside the approved scope. Destructive database resets, drops, irreversible cleanup, or mass deletion require explicit user approval even for the local development database.

## 10. Git and pull-request workflow

The permanent branch is `main`. There is no `develop` branch.

For an OpenSpec feature:

```text
main
  └── feature/<change-id>
```

Example:

```text
OpenSpec change: add-observation-definition-api
Git branch:      feature/add-observation-definition-api
```

Every significant feature uses a PR. `main` should be protected in GitHub with the CI check required before merge. Use squash merge so one completed OpenSpec change becomes one logical commit on `main`.

### 10.1 Conservative agent Git permissions

Agents may autonomously:

- create a local feature branch;
- modify files in approved scope;
- run checks/tests;
- create local commits.

Explicit user approval is required before agents:

- push to GitHub;
- create/update a PR;
- merge a PR;
- modify `main` directly;
- force-push or rewrite remote history.

## 11. Choosing direct change vs OpenSpec

Ask one question first:

> Is the expected behavior already fully defined and is the change mechanical/local, or are we defining/changing behavior?

Use a direct change when the answer is clearly mechanical/local. Use OpenSpec when behavior, contract, interaction, lifecycle, or acceptance criteria need to be defined or changed.

Examples of direct changes:

- correct a typo;
- reformat code;
- refactor without behavior change;
- add a test for already-defined `/health` behavior;
- change a purely presentational label with no new interaction semantics.

Examples requiring OpenSpec:

- add an Observation Definition API;
- add an endpoint that starts an ObservationRun;
- change a structured result contract;
- change LensRun status/failure semantics;
- add a new analytical agent/tool or change its budget;
- add a semantically meaningful database model;
- define cross-module interaction.

If the classification is unclear, the agent should propose the classification instead of silently deciding.

## 12. OpenSpec workflow for this project

The repository starts with the `core` OpenSpec profile:

```text
explore → optional thinking
propose → create the planning artifacts
apply   → implement the approved tasks
update  → revise the planning artifacts when explicitly approved
sync    → merge deltas early only when intentionally needed
archive → merge deltas into canonical specs and archive the change
```

The project adds two governance constraints on top of OpenSpec's mechanics:

1. human approval is mandatory before apply;
2. archive happens in the feature branch before the PR is opened/merged.

### 12.1 Standard feature lifecycle

```text
1. Create feature/<change-id> from main.
2. Read AGENTS.md.
3. Read docs/architecture/README.md.
4. Read the relevant architecture/ADR/contract files.
5. Explore first when the requirement is still unclear.
6. Propose the OpenSpec change.
7. Run `$ipo-review-plan <change-id>` and correct planning findings.
8. Obtain explicit human approval.
9. Apply/implement the approved tasks.
10. Run `make check`.
11. Run `$openspec-verify-change <change-id>` when the optional verify workflow is installed.
12. Run `$ipo-review-implementation <change-id>` in a fresh reviewer context when practical.
13. Triage findings, apply targeted fixes, and use `$ipo-verify-findings` until blocking findings are resolved or withdrawn.
14. Archive the OpenSpec change in the feature branch.
15. Review the resulting `openspec/specs/` and archive diff.
16. Run `make check` again if archive changed validated content.
17. Commit the completed branch.
18. Open a PR.
19. Let required GitHub Actions CI pass.
20. Review code + specs + Reviewer Notes.
21. Squash merge to main.
```

The archive-before-PR convention intentionally makes one PR contain the implementation, the canonical spec update, and the archived change. This avoids an additional post-merge archive PR in a solo-development workflow.



### 12.2 Approval gate

The agent must not treat generated planning artifacts as automatically approved.

```text
proposal/specs/design/tasks
          ↓
      user review
          ↓
  explicit approval
          ↓
        apply
```

If implementation later proves the approved scope or behavior needs revision:

```text
STOP
→ explain the mismatch
→ request approval
→ update OpenSpec artifacts
→ re-review the plan
→ continue implementation
```

The agent may update task checkboxes and make local implementation choices inside approved boundaries without reopening the entire specification.

### 12.3 Reusable review skills

The project maintains reusable report-only review skills under `.agents/skills/ipo-*`:

- `$ipo-review-plan <change-id>` — architecture/spec/design/task review before human approval;
- `$ipo-review-implementation <change-id>` — independent implementation/code/test review before archive;
- `$ipo-verify-findings <change-id> ...` — bounded re-check of accepted findings after targeted fixes.

The optional official `$openspec-verify-change <change-id>` workflow should be enabled alongside the core OpenSpec workflows and run after implementation. Configure it with `openspec config profile`, keep the core workflows selected, enable `verify`, then run `openspec update` for the repository.

Use `docs/development-workflow.md` as the concise contributor-facing process.


## 13. OpenSpec architecture references

For a behavioral change, OpenSpec artifacts should identify the relevant architecture constraints rather than restating them.

A proposal/design may contain:

```markdown
## Architecture References

- `docs/architecture/02_architecture_principles_and_runtime.md`
- `docs/architecture/06_runtime_contracts_and_execution_semantics.md`
- ADR-043 — Observation Orchestrator is a deterministic workflow component
```

Use `N/A` only when the change genuinely has no architecture dependency.

When reading architecture context, do not load every architecture file automatically. Start with `docs/architecture/README.md`, then follow only the relevant references.

## 14. Dependency changes

Agents may recommend a dependency but may not add/remove one without approval.

A dependency proposal should answer:

1. What dependency is being proposed?
2. Why is it needed?
3. What problem does it solve?
4. Can the change reasonably be implemented without it?
5. What does it add/change in the approved stack?

After explicit approval, update the manifest and lockfile normally.

## 15. Agent-instruction maintenance

Start with only the root `AGENTS.md`.

Create a nested `AGENTS.md` only when a subsystem has stable rules that:

- apply only to that subtree;
- matter across more than one change;
- are repeatedly needed in agent prompts/reviews.

If an agent detects that pattern, it should suggest a nested instruction file. It must not create one automatically.

Architecture rules still belong in architecture docs/ADRs; feature requirements still belong in OpenSpec. `AGENTS.md` is only for how development agents should work.

## 16. GitHub Actions CI

The initial CI is intentionally minimal:

```text
backend  → Ruff + pytest
frontend → ESLint + build
OpenSpec → strict validation
```

No PostgreSQL service container is started yet because bootstrap tests do not require database integration. Add PostgreSQL to CI only when persistence integration tests actually need it.

Do not add coverage thresholds, security scanners, type-check gates, or other checks merely for completeness. Add them later when they solve a concrete problem.

## 17. Pull-request review order

For an OpenSpec feature, a useful review order is:

1. read the PR Summary;
2. inspect the OpenSpec change/archive and resulting canonical spec;
3. inspect Architecture References;
4. read Reviewer Notes for non-obvious implementation details;
5. review the code/tests;
6. confirm `make check`/CI passes;
7. verify implementation is within approved scope;
8. squash merge.

Use Reviewer Notes to preserve useful implementation-level reasoning without turning every local choice into an ADR. If the note reveals a new architectural or behavioral decision, it should be moved back into the appropriate approval/specification process rather than hidden in the PR description.

## 18. Project-specific examples

### Example 1 — Small direct change without OpenSpec

Scenario: the `/health` endpoint already has the approved bootstrap behavior `{"status":"ok"}`. You notice the test name is unclear and want to improve the test structure without changing behavior.

Create a small branch:

```bash
git switch main
git pull --ff-only
git switch -c chore/clarify-health-test
```

Ask Codex/OpenCode for the mechanical change. The agent should read `AGENTS.md` and the directly relevant backend/test files. It does not need to create an OpenSpec change or read the whole architecture package because behavior is already defined.

Run:

```bash
make check
```

The PR uses:

```text
OpenSpec Change: N/A - direct change
Architecture References: N/A
```

If the change unexpectedly alters the health response contract, stop treating it as direct and create an OpenSpec change instead.

### Example 2 — Normal feature: Observation Definition API

Scenario: implement a first real feature that creates and reads Observation definitions.

Start from clean `main`:

```bash
git switch main
git pull --ff-only
git switch -c feature/add-observation-definition-api
```

Read the repository rules and relevant architecture context:

```text
AGENTS.md
docs/architecture/README.md
relevant Observation/Lens concept, runtime, contract, ADR, and backlog sections
```

If the feature shape is already clear, ask the agent to propose it directly. In Codex:

```text
$openspec-propose
```

A useful request is:

```text
Create the OpenSpec change `add-observation-definition-api` for the minimal
Observation Definition create/read API required by Phase 1. Use the repository
architecture as a constraint. Do not resolve any Open or Deferred architecture
question implicitly. Include explicit Architecture References.
```

OpenSpec should produce the planning artifacts under:

```text
openspec/changes/add-observation-definition-api/
```

Review:

- proposal scope;
- delta specs and scenarios;
- design;
- task list;
- architecture references;
- any dependency/schema implications.

Do not allow the agent to apply immediately. Approve explicitly only when the plan is correct.

Then, in Codex:

```text
$openspec-apply-change
```

The agent implements only the approved tasks. It may create normal Alembic migrations because schema work is already approved. It may not add a new dependency unless you approve that dependency separately.

Run:

```bash
make check
```

When tasks are complete and the implementation is verified, archive the change in the feature branch. In Codex:

```text
$openspec-archive-change
```

Or interactively in the terminal:

```bash
openspec archive add-observation-definition-api
```

Review the diff carefully:

```bash
git status
git diff
```

Confirm that:

- canonical `openspec/specs/` now describes the accepted behavior;
- the change moved to `openspec/changes/archive/...`;
- no unrelated architecture decisions were altered;
- implementation and specs still agree.

Run `make check` again when useful, commit, then ask for approval before push/PR creation. The PR targets `main`, passes CI, and is squash-merged.

### Example 3 — Feature discovers an unresolved architecture question

Scenario: a later feature proposes an endpoint or workflow that starts an `ObservationRun`. During implementation, the agent discovers that correct behavior depends on a triggering/lifecycle question that the architecture backlog still marks open, for example overlap behavior when a new trigger arrives while another ObservationRun is already running.

Start normally:

```bash
git switch -c feature/start-observation-run
```

If the requirement is fuzzy, use exploration before proposing. In Codex:

```text
$openspec-explore
```

Then propose the bounded feature:

```text
$openspec-propose
```

Suppose the proposal or implementation discovers that overlap semantics must be chosen before the feature can be correct.

The agent must not decide "reject duplicate runs", "queue them", or "run them concurrently" merely because one option is easy. The correct flow is:

```text
STOP implementation
→ identify the exact open architecture question
→ show the relevant backlog/ADR/context reference
→ explain which implementation choices depend on it
→ ask the user for an explicit architecture decision
```

After the user makes the decision, architecture docs/ADR remain read-only until the user explicitly authorizes their update. Once authorized:

1. update the relevant ADR/architecture/backlog/changelog documents;
2. update the OpenSpec change to reflect the now-approved behavior;
3. re-review the revised plan;
4. obtain explicit approval again;
5. resume implementation.

In Codex, an approved revision can use:

```text
$openspec-update-change
```

The important property is not the command itself; it is that the architecture decision occurs consciously before code commits to one semantic path.

## 19. Known architecture-document synchronization item

The current architecture package predates some implementation-stack selections made during workspace design. In particular, the open-decisions document may still list database technology/schema and workflow/orchestration technology as open.

For implementation work in this repository, the approved baseline is already:

```text
Database: PostgreSQL
Persistence: SQLAlchemy async + Alembic
PostgreSQL driver: Psycopg 3
Top-level deterministic orchestration: plain Python + asyncio
Application architecture: modular monolith
```

This is a documentation synchronization gap, not permission for an agent to choose a different implementation stack. Do not silently edit the architecture package to remove the stale items. Synchronize that documentation only through an explicitly approved architecture/docs update.

## 20. Troubleshooting

### OpenSpec commands/skills do not appear

From the repository root:

```bash
openspec update
```

Then restart the agent/IDE session. Codex does not provide `/opsx` autocomplete because its OpenSpec integration is skills-only; use the generated `$openspec-*` skill names. For OpenCode, inspect the generated files and the exact startup output from `openspec init`.

### OpenSpec validation fails

Run:

```bash
openspec validate --all --strict
```

Read the reported change/spec path. Validation is structural. Do not weaken or delete a specification just to make the command green. Fix the actual artifact structure or, when the change intentionally has no behavioral spec, follow OpenSpec's explicit tooling/refactor mechanism rather than inventing an empty behavioral requirement.

### `uv sync` cannot find Python 3.13+

Keep Ubuntu's system Python unchanged and install a compatible interpreter through `uv`:

```bash
uv python install 3.13
make setup
```

### Backend cannot connect to PostgreSQL

Check:

```bash
docker compose ps
cat .env
```

Verify the database service is running and the root `DATABASE_URL` matches the Compose credentials/port.

### Frontend environment value is sensitive

Do not use it in the frontend. Browser-visible environment values are not secrets. Move the sensitive value to the backend environment and expose only the minimum server-mediated behavior needed by the UI.

## 21. When to extend the development environment

Do not add tools preemptively. Consider an addition only after a concrete need appears, for example:

- frontend testing when real UI behavior becomes meaningful;
- PostgreSQL service in CI when integration tests need persistence;
- a nested `AGENTS.md` when stable subsystem-specific rules repeat;
- stricter type/coverage/security gates when they catch a real class of defects;
- a UI component library when real admin screens are being built;
- PydanticAI in the first approved production agent feature that requires it. ADR-152 records the MVP framework decision; the dependency is intentionally not added preemptively.

The default answer to "might this be useful later?" is to keep the workspace simple until the need is demonstrated.
