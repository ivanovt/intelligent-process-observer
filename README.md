# Intelligent Process Observer

Intelligent Process Observer is the implementation workspace for a master-thesis MVP focused on intelligent multi-agent observation, anomaly analysis, and supervision of technological processes.

The repository is a monorepo. Architectural decisions are maintained separately from implementation specifications: the architecture package under `docs/architecture/` is the authoritative source for architecture and ADRs, while OpenSpec is used to define concrete behavioral changes before implementation.

## Development baseline

- Windows host with WSL2
- Ubuntu 22.04 LTS inside WSL2
- repository stored in the WSL Linux filesystem
- VS Code connected to WSL
- Docker Engine running directly in WSL2
- Python >= 3.13, managed with `uv`
- FastAPI, Pydantic, SQLAlchemy async, Alembic, PostgreSQL, Psycopg 3
- Node.js >=24.15.0, React, TypeScript, Vite, Tailwind CSS 4, npm
- OpenSpec core workflows plus the optional `verify` workflow
- Codex as the primary coding agent, with OpenCode also supported

## Quick start

From the repository root:

```bash
make setup
make db-up
```

Start the backend in one terminal:

```bash
make backend
```

The shallow health endpoint is available at:

```text
http://localhost:8000/health
```

Start the frontend in another terminal:

```bash
make frontend
```

Run the complete local verification gate before a pull request:

```bash
make check
```

The frontend requires Node.js `>=24.15.0`. Its Vite development server proxies
relative `/api` requests to the local backend; run frontend tests with
`cd frontend && npm run test` (or use `make test` for both test suites).

### Configure Prometheus metric sources

Metric sources are configured on the backend through the optional
`PROMETHEUS_SOURCES` environment variable. Its value is a JSON array, so one backend
instance can expose multiple Prometheus systems to the Metric Lens editor. Each entry
requires a unique machine-friendly `id`, a display `name`, a `base_url`, and exactly
one supported `credentials` object.

For local development, copy `.env.example` to the untracked root `.env` file and add
the configuration there. A Bearer-token source uses this shape:

```dotenv
PROMETHEUS_SOURCES=[{"id":"primary-prometheus","name":"Primary Prometheus","base_url":"https://prometheus.example.invalid/prometheus","credentials":{"type":"bearer_token","token":"replace-with-secret-token"}}]
```

Basic authentication uses this shape:

```dotenv
PROMETHEUS_SOURCES=[{"id":"secondary-prometheus","name":"Secondary Prometheus","base_url":"https://secondary.example.invalid/prometheus","credentials":{"type":"basic_auth","username":"replace-with-reader-username","password":"replace-with-secret-password"}}]
```

To configure multiple sources, place multiple source objects in the same JSON array.
Keep real credentials only in the local `.env` or deployment environment: never commit
them or put them in `frontend/.env` or `VITE_*` variables. After changing the value,
restart the backend, open **Data Sources** in the UI, and select **Refresh sources**.
The refresh action reads the running backend configuration; it does not reload changed
environment variables without a backend restart.

See [`.env.example`](.env.example) and the
[development guide](docs/development-guide.md#53-prometheus-metric-provider-configuration-and-operation)
for the canonical examples and operational constraints.

## OpenSpec bootstrap

OpenSpec-generated agent skills and commands are generated by the installed OpenSpec CLI rather than maintained by hand. During the initial workspace bootstrap, run from the repository root:

```bash
openspec init --tools codex,opencode --profile core
```

Review the generated files and commit them as part of the bootstrap pull request. The project also uses the optional OpenSpec `verify` workflow. Enable it with `openspec config profile` (keep the core workflows selected and add `verify`), then apply the profile to the project or run `openspec update`.

After upgrading the OpenSpec CLI, refresh the generated integration files with:

```bash
openspec update
```

## Sources of truth

Use the following distinction consistently:

- `docs/architecture/` defines accepted architecture, architectural constraints, ADRs, and open/deferred decisions.
- `openspec/changes/` defines the behavioral change currently being planned or implemented.
- `openspec/specs/` accumulates accepted functional behavior from completed changes.
- source code implements those decisions and specifications.

Do not infer requirements from architecture items marked `Open` or `Deferred`.
